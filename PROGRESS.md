## 2026-09-11 — Scope expanded to 4 predictor models: qualifying + race-time added

- **User explicitly changed scope** (confirmed via direct question, not assumed) from "exactly 2 predictor models" to 4, adding a qualifying-result predictor and a race-time predictor. AGENTS.md's hard scope constraint updated to name all 4 targets and why the qualifying model needs a different feature set — that section is now the canonical reference, not this entry.
- **`qualifying`**: predicts qualifying gap-to-pole *before qualifying happens*. This is genuinely not "reuse the same feature pipeline" — traced every existing feature-layer file (`driver_features.py`, `team_features.py`, `relative_features.py`, `strategy_features.py`) plus `ingest.py`'s weather capture to work out exactly which columns would leak this race's actual qualifying/grid/compound result into a model meant to predict qualifying before it exists. Real finding: weather columns are captured from the **race** session (Sunday), not qualifying/practice — so they had to be dropped entirely for this model, not just masked, since no qualifying-day weather is ingested at all. New restricted feature set lives in `src/models/features.py` as `QUALI_SAFE_FEATURE_COLS`, enforced by a leakage-safety assertion in `tests/test_rolling_predict.py`. Result: baseline (predict team's historical quali pace) 0.801s MAE → tuned 0.705s. Top SHAP: practice_pace, team_quali_pace, driver_recent_form — exactly the expected pre-quali story.
- **`race_time`**: predicts gap to the race winner in seconds (0 for the winner), from FastF1's `results['Time']` (already gap-to-winner for non-winners; winner's own row is their absolute duration, remapped to 0). DNF/not-classified rows get no target value and are dropped, same honest-gap handling as every other target. Same full pre-race feature set as finish_position/quali_delta (this target resolves at the race, unlike qualifying). Result: baseline (race's own mean gap-to-winner) 21.208s → tuned 19.709s. SHAP top feature was `longest_straight_m` — plausible (bigger straights → bigger speed-differential time gaps), and the hard/easy-overtaking-track SHAP split came out *opposite* in direction from the finish-position model's (higher at easy tracks, not hard) — plausible mechanism (hard-to-pass tracks bunch the field together in time even when position-wise stuck, so grid position's effect on the raw time gap is compressed there), not verified further, flagged as an open finding same as Phase 3's similar non-replicating SHAP result.
- **Real gotcha during the raw-data backfill**: adding `gap_to_winner_seconds` required a new raw column, so all 105 cached races needed re-ingesting. Assumed `--force` re-ingest would be fast since FastF1's own local disk cache was warm (1.2GB, all 105 races) — wrong assumption: `--force` reprocesses the *entire* `ingest_race()` (laps, weather, practice, quali, not just results), which is much more data than the local cache apparently had fully warm, and it burned through the ~500/hour courtesy rate limit fast. Worse, it then got stuck retrying **future, not-yet-run 2026 races** (e.g. Las Vegas) for 90+ minutes of 9s-backoff retries, because a request for a race with no data yet apparently returns the same error shape as a real rate limit once the quota is actually exhausted — so it couldn't tell "this race doesn't exist yet" from "wait and retry." Caught by checking raw file mtimes (all 105 known races had already been rewritten correctly) and killing the stuck process rather than waiting out its ~3h retry cap. Verified the backfilled data directly (winner rows all have gap=0, no mismatches, 2124 rows, ~19% null rate matching DNF/not-classified). **Lesson for next time a raw column needs backfilling: don't reach for `--force` on the whole pipeline — write a targeted script that re-fetches only the new field for already-cached races.**
- All 4 models retrained on the rebuilt `model_matrix.parquet` (43 columns now: 33 features + 4 targets + 6 identifiers). finish_position/quali_delta metrics unchanged within noise (3.134/3.384 and 3.016/3.384 MAE) — confirms the backfill didn't disturb the existing feature/target data.
- `tests/test_rolling_predict.py` extended: race_time joins the existing rolling-stage check (it resolves post-race like the other two); qualifying gets its own single-stage plausibility + leakage-safety test (asserts none of the excluded this-race-actual columns ever end up in `QUALI_SAFE_FEATURE_COLS`).
- `live_predict.py` now reports all 4 predictions per driver; verified end-to-end against the real upcoming Madrid race (2026 round 14, zero sessions run) — `predicted_qualifying_gap` is the one genuinely new live capability (a forecast for a session that hasn't happened), the other three still sharpen as real session data arrives same as before.

## 2026-09-11 — Phase 2 complete: finishing-position predictor trained and evaluated

- **Blocker hit and fixed:** FastF1 self-enforces a ~500-calls/hour courtesy rate limit on its free public data sources.
  1. First attempt burned through it in ~7 min with no backoff, silently skipping most races — fixed by making `fastf1_client.load_session` retry-on-`RateLimitExceededError` instead of failing the race.
  2. The retry backoff was initially a flat 60s sleep per attempt, which badly under-uses the real refill rate (~1 call/7.2s) once a race needs many genuinely-fresh calls (e.g. FP2/FP3 never touched before) — a session could stall 40+ minutes making only ~1 call of progress per minute. Fixed by dropping the backoff to 9s (just above the natural refill interval) and raising the attempt cap to keep the same ~3h ceiling. This is tuning our own use of the legitimately allowed rate, not an attempt to bypass the limit — restarting the process to reset FastF1's in-memory counter and get a fresh burst was deliberately avoided as against the spirit of the library's own courtesy throttle.
  3. Practice pace briefly went FP1-only (~40% fewer calls/race) to fit the original slow backoff; reverted to full FP1-FP3 once the backoff was fixed, per explicit request to keep the fuller practice signal and full Q1/Q2/Q3 quali data.
