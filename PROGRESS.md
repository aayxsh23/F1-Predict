## 2026-09-11 — Phase 6 complete: LangGraph live-standings agent

- **Real architecture decision, evidence-based not assumed**: tested the local Llama 3.2 1B Instruct's LangChain tool-calling for real (`ChatHuggingFace.bind_tools()` + `.invoke()`) before committing to a ReAct-style agent design — it came back with zero tool calls, and the rendered prompt showed no tool schema had even reached the model. Built as an explicit `StateGraph` instead: the graph does the multi-step orchestration (classify → fetch/compute → synthesize), the LLM only handles picking one of a few known intents and (for the one catch-all case with no structured data) writing free-form answers.
- **`src/agent/f1_api.py`**: thin Jolpica-F1 (Ergast-compatible, the free successor API this project identified back in Phase 1's planning) client — driver standings, constructor standings, season schedule with sprint-weekend flags. Verified against the real, live API (2026 season, round 13 completed, 23 drivers, 11 constructors, 6 sprint rounds).
- **`src/agent/scenarios.py`**: the actual reasoning behind "what does Norris need to win the title" — remaining-points pool (accounting for sprint points), mathematical-elimination check, points needed to draw level assuming the rival scores zero more. **Real design bug caught by writing the test first**: an earlier version computed "points needed to guarantee ahead of the rival regardless of what the rival does" — arithmetically correct, but that number is *only ever achievable when the driver already leads* (a trailing driver's rival can always just match their result and keep the lead), making it useless for the plan's own example of a driver in 4th. `tests/test_scenarios.py` asserting a concrete expected value caught this immediately (got `None` back, not a number) — redesigned around "points needed if the rival scores nothing more," the standard framing real title-race analysis uses, which is always well-defined.
- **`src/agent/graph.py`**: `classify_node` uses heuristic keyword matching first, LLM only as a last resort — flipped from an LLM-first design after a real test showed "who is leading the constructors championship?" misclassifying to `title_scenario` (the model over-weighted the word "championship"). **Second real bug**: the three structured intents (driver standings, constructor standings, title scenario) originally handed their real, correctly-fetched data to the LLM to phrase into a final answer — a real test showed the base model hallucinating even with correct data verbatim in the prompt (a fabricated "red-carbon fiber wall" at Zandvoort, an invented driver code "B2", a gap answer of "0.7 (or 7.0 seconds)" that doesn't parse and isn't in the data at all). Fixed by templating the answer deterministically straight from the computed data for all three structured intents — no LLM in that path at all; only the `general` catch-all (genuinely no structured data to template) still goes through the LLM, with the same honest quality caveat `rag/chat.py`'s open-ended path already carries.
- **Third real bug**: follow-up questions inheriting the previous turn's classified intent (needed for "and what about the gap to 2nd?" to correctly reuse `constructor_standings`) was initially too aggressive — it inherited for *any* question that didn't match a keyword, so a completely unrelated question ("when did F1 start using turbo hybrid engines?") got wrongly answered with two-turns-stale constructor standings. Fixed by requiring an explicit continuation marker ("and...", "what about...", "how about...") at the start of the question before inheriting — a real discourse signal, not just "didn't match anything else."
- **Memory**: `langgraph.checkpoint.memory.MemorySaver` keyed by `thread_id`; `ask()` only ever passes `{"messages": [...]}` as input (not a fresh `intent`/`data` reset every call), since LangGraph merges input into checkpointed state rather than replacing it — that's what lets `classify_node` see the previous turn's `intent` for the continuation check above.
- **Verified end-to-end** against the real live Jolpica-F1 API (not mocked) across all four intents plus a follow-up and an unrelated-topic non-inheritance check: driver standings (Norris: 171 pts, 4th), constructor standings (Mercedes 468 vs Ferrari 346, gap 122 — matches real data exactly), the plan's own title-scenario example (Norris 96 points behind Antonelli, needs 97 to draw level assuming Antonelli scores zero more), and correct routing on both a same-topic follow-up and an unrelated new question.
- Added `tests/test_scenarios.py` (6 checks, the math) and `tests/test_agent.py` (8 checks, routing + answer-templating — each one a direct regression test for a bug found above) and `src/agent/cli.py` (interactive test harness matching `rag/chat.py`'s pattern).
- Also fixed a stale doc: AGENTS.md's repo-layout comment had labeled `src/agent/` as "Phase 5" (left over from before the qualifying/race-time scope expansion never actually renumbered anything, but this comment was just wrong) — corrected to "Phase 6."
- **Status:** Phase 6 done — a genuine LangGraph agent, live data, multi-step scenario reasoning, working memory, all verified against the real API. Every intent that has real structured data behind it (the three that matter most) now uses zero LLM-generated numbers, only real computed ones.
- **Next:** Phase 7 — FastAPI backend + automation + deployment. Detailed forward-looking design already exists in `phase7-ui-backend-plan.md`.

Fine for a test harness; would need its own fine-tuning examples if this format becomes a real product surface later.

## 2026-09-11 — Phase 5 complete: LoRA fine-tune trained and swapped in

- **Dataset** (`src/rag/build_finetune_dataset.py` -> `src/rag/training_data/explanations.jsonl`, 108 examples, not yet committed — small enough to commit per the earlier plan, but sitting as an uncommitted working-tree file like everything else this session pending the user's go-ahead): one example per (circuit, target) combination that actually has valid data, built by running the *real* inference pipeline (real prediction, real SHAP, real retrieval query, real retrieved chunks) and composing an accurate, grounded completion from a hand-built per-feature sentence-template bank + a per-circuit fact dictionary (drawn from the corpus this agent authored). Two real bugs caught and fixed before this was usable as training data, both on first inspection of the output, not assumed correct:
  1. **Every generated sentence was grammatically broken** — `"{phrase} {direction}"` concatenated a noun phrase directly against a bare adjective ("Historical performance on this tyre compound higher (worse finish)...") with no verb. Fixed by inserting "pushed the prediction" before the direction phrase.
  2. **Circuit facts silently went missing for aliased locations** — `ingest.py`'s raw `location` column uses whatever FastF1 called the circuit that season (`"Monte Carlo"` from 2026 onward, not `"Monaco"`), and the new `CIRCUIT_FACTS` dict was keyed by the older canonical name, so recent rows fell through to a generic filler fact instead of the real Monaco-specific one. Fixed by reusing `circuit_reference.py`'s existing `LOCATION_ALIASES` (not a second copy of it) before the lookup.
- **Training**: `src/rag/finetune.py`, QLoRA via `trl.SFTTrainer` (4-bit nf4 base + `peft.LoraConfig`, r=16, all 7 attention/MLP projections). **Real API gotcha**: `assistant_only_loss=True` (mask the loss to just the completion, not the prompt) failed outright — TRL requires `{% generation %}` markers in the tokenizer's chat template to know which tokens are "assistant" tokens, and Llama 3.2's default template doesn't have them. Fixed by training on full-sequence loss instead (documented as a deliberate `ponytail:`-tagged simplification in the code, with the patch-the-template alternative named as the upgrade path) rather than fighting the template. 4 epochs, batch size 1 x grad-accum 8, ~36 min on the RTX 3050 Ti's 4GB VRAM (slow mostly from gradient checkpointing, not from the model being large). Loss dropped from its early value down to 0.45, token accuracy up to 0.92 by the end — healthy convergence for a 108-example set, no instability.
- **Adapter swap required zero changes outside `finetune.py` itself** — `src/rag/llm.py`'s `generate()` already checked `ADAPTER_DIR.exists()` and wraps the base model with `PeftModel.from_pretrained()` when it does, exactly per the plan's "only the generation call changes" design from two sessions ago.
- **Qualitative comparison, the real point of this phase**: same Monaco `finish_position` prediction, base model vs. fine-tuned, side by side.
  - Base: rambling, and at one point directly self-contradicting — claimed the team has "a strong chance of overhauling other drivers and finishing near the front" for a driver predicted to finish **15th**, two sentences after correctly stating Monaco is the hardest circuit on the calendar to overtake at.
  - Fine-tuned: four tight sentences, consistently framed around "pushed the prediction higher (worse finish)" for a bad predicted position, correctly citing the same Monaco overtaking-difficulty fact without contradicting itself.
  - Also tested on a genuinely held-out row (an earlier Monaco race never used in training, `race_time` target) to check for real generalization vs. memorization — produced correctly-directioned, coherently-phrased output that wasn't a verbatim template match, confirming it learned the *style/discipline*, not just 108 fixed answers.
- **Recurring session gotcha, worth calling out since it hit three separate times today**: printing non-ASCII text (©, ≈, é) to a Windows console/pipe without `PYTHONIOENCODING=utf-8` set crashes with `UnicodeEncodeError` on the cp1252 default codepage — every time, it was the *display* that broke, never the underlying UTF-8 file content (verified by checking raw bytes once, rather than trusting console output). Worth setting `PYTHONIOENCODING=utf-8` up front on any ad hoc test command on this machine rather than re-discovering this per script.

## 2026-09-11 — Phase 4 confirmed working end-to-end; Llama access unblocked

- **Hugging Face gated-access blocker from the previous entry is resolved** — `hf_hub_download('meta-llama/Llama-3.2-1B-Instruct', 'config.json')` now succeeds (was a pending/incomplete access request on the HF side, not a token problem).
- **Real bug found and fixed on first real run**: `src/rag/llm.py`'s `generate()` called `tokenizer.apply_chat_template(..., return_tensors="pt")` expecting a bare tensor back (the historically-documented behavior), then did `inputs.shape[1]` and passed `inputs` positionally to `model.generate()`. In the installed `transformers==5.17.0`, `apply_chat_template(..., return_tensors="pt")` actually returns a `BatchEncoding` (dict of `input_ids`/`attention_mask`), not a tensor — so `.shape` doesn't exist on it directly, and passing it positionally to `generate()` is wrong. Fixed by passing `return_dict=True` explicitly, unpacking `**inputs` into `model.generate()`, and reading `inputs["input_ids"].shape[1]` for the prompt-length slice. Another instance of the same lesson as the earlier `torch` CPU/CUDA gotcha: a library's documented/remembered API shape can quietly drift version to version, and the failure here was a hard crash (good) rather than silently wrong output (would've been worse).

## 2026-09-11 — Scope expanded to 4 predictor models: qualifying + race-time added

- **`qualifying`**: predicts qualifying gap-to-pole *before qualifying happens*. This is genuinely not "reuse the same feature pipeline" — traced every existing feature-layer file (`driver_features.py`, `team_features.py`, `relative_features.py`, `strategy_features.py`) plus `ingest.py`'s weather capture to work out exactly which columns would leak this race's actual qualifying/grid/compound result into a model meant to predict qualifying before it exists. New restricted feature set lives in `src/models/features.py` as `QUALI_SAFE_FEATURE_COLS`, enforced by a leakage-safety assertion in `tests/test_rolling_predict.py`. Result: baseline (predict team's historical quali pace) 0.801s MAE → tuned 0.705s. Top SHAP: practice_pace, team_quali_pace, driver_recent_form — exactly the expected pre-quali story.
- **`race_time`**: predicts gap to the race winner in seconds (0 for the winner), from FastF1's `results['Time']` (already gap-to-winner for non-winners; winner's own row is their absolute duration, remapped to 0). DNF/not-classified rows get no target value and are dropped, same honest-gap handling as every other target. Same full pre-race feature set as finish_position/quali_delta (this target resolves at the race, unlike qualifying). Result: baseline (race's own mean gap-to-winner) 21.208s → tuned 19.709s. - **Real gotcha during the raw-data backfill**: adding `gap_to_winner_seconds` required a new raw column, so all 105 cached races needed re-ingesting. Assumed `--force` re-ingest would be fast since FastF1's own local disk cache was warm (1.2GB, all 105 races) — wrong assumption: `--force` reprocesses the *entire* `ingest_race()` (laps, weather, practice, quali, not just results), which is much more data than the local cache apparently had fully warm, and it burned through the ~500/hour courtesy rate limit fast. Verified the backfilled data directly (winner rows all have gap=0, no mismatches, 2124 rows, ~19% null rate matching DNF/not-classified). **Lesson for next time a raw column needs backfilling: don't reach for `--force` on the whole pipeline — write a targeted script that re-fetches only the new field for already-cached races.**

- **Blocker hit and fixed:** FastF1 self-enforces a ~500-calls/hour courtesy rate limit on its free public data sources.
  1. First attempt burned through it in ~7 min with no backoff, silently skipping most races — fixed by making `fastf1_client.load_session` retry-on-`RateLimitExceededError` instead of failing the race.
  2.   3. Practice pace briefly went FP1-only (~40% fewer calls/race) to fit the original slow backoff; reverted to full FP1-FP3 once the backoff was fixed, per explicit request to keep the fuller practice signal and full Q1/Q2/Q3 quali data.
